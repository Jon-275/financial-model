# Retirement Planner enhancement plan

Status on November 25, 2026. The delivery ledger tracks implementation and release evidence against these contracts.

## Baseline and intended outcome

Use the published `v1.0.0` workbook and source commit `6573e1e` as the comparison point. The release records Excel for Mac 16.115 and a reconciled 1,000-pair run with 33 stresses. It already includes a native runner, guidance for 100 and 1,000 pairs, a fictional walkthrough, a six-page report, and federal and California calculations. The published 8-minute standard and 33-minute full-range figures are historical measurements. D1 recorded a fresh 100-pair Mac baseline. Windows remains unverified. [Release and evidence](https://github.com/Jon-275/financial-model/releases/tag/v1.0.0) · [D1 baseline](desktop-verification.md#november-24-2026-baseline)

The target is a faster, easier-to-use local planner with reproducible financial results and a supportable Windows distribution path. Keep Excel as a first-class interface and retain inspectable ledgers, fictional release fixtures and offline household data. Verify each supported platform and tax jurisdiction before adding it to release claims. Require a versioned, independently reconciled calculation contract before building an interactive web interface.

## Development and review

1. Use a worktree and topic branch per concern. Start with a short PR description covering the proposed behavior, inputs and outputs, invariants, prior-release behavior, fixtures, and rollback. Make each stack commit buildable and keep individual PRs within the dev-loop size budget. Review generated XLSM and PDF artifacts with their source and evidence even though binary files count as zero lines.
2. Build the failing boundary or regression case before behavior changes. Verify formula, independent Python, saved workbook and presentation at the layers affected. For execution-state changes, test selection, cancellation, errors, retries, protection restoration and stale results. Keep performance measurement independent of financial output and exclude personal data from review artifacts.
3. Run `devloop doctor --check`, changelog and size checks when available, then the relevant workbook and site checks. Keep `Workbook checks`, `Greptile Review`, `Gemini Review` and thread resolution required. On the latest PR head, wait for reviewers, answer every finding with its disposition and evidence, and push the fixes together. Merge through PRs after the checks pass. Use merge commits for stacks and retarget the dependent PR before deleting its base branch. [Maintainer checks](../../tests/README.md) · [Branch rules](https://github.com/Jon-275/financial-model/rules/27295551)
4. During D4, test opened, updated, labeled and unlabeled PRs and record the exact required check name. The upstream advisory doctor job skips label-only events. If the skipped check can satisfy protection, use a dedicated required drift job that cannot be bypassed by a metadata-only event. Test failure and recovery on a disposable PR before changing rules. Keep size and missing changelog entries advisory until the team has evidence that tighter rules help.
5. For E2, replay representative financial, VBA, workflow and documentation changes through the candidate reviewer. Compare findings, silent omissions, review time and cost. Require parity for `.bas` and `.fragment` files, full bounded source coverage, latest-head checks, explicit model failure and privacy exclusions. Read trusted base configuration and PR data through git without executing PR code in secret-bearing jobs. Continue current reviewers until the replacement proves parity and rollback. Keep model/API changes in a separate PR. [Dev-loop adoption](https://github.com/Jon-275/dev-loop/blob/v0.10.0/docs/adoption.md) · [Existing reviewer tests](../../tests/gemini_review.test.mjs)

## Enterprise distribution and operations

- Assign a release owner, independent financial reviewer, desktop publisher and support owner. Record which Microsoft 365 channels, architectures and locales are supported. Exercise the managed channel on a licensed, isolated interactive desktop with a reviewed commit and fictional inputs. Keep fork CI on isolated workers without release or desktop credentials.
- Build an immutable release candidate once. Its evidence binds source, dependency and tax-data revisions, the fixture set, workbook/PDF hashes, signing status and exact validation results. Financial outputs must be reproducible under pinned inputs. Build timestamps and signing can change bytes, so promote the exact candidate that was tested. Tag and verify the workbook, example PDF, license and checksum set, then make the site use those approved artifacts. [Publishing process](../publishing.md)
- Use approved publisher signing and managed distribution for enterprise macros. Establish certificate storage, renewal and revocation with desktop IT. Test the signed artifact in its distribution channel, under the target policy. If its bytes differ from the public workbook, give it a separate manifest and support record. A checksum validates artifact identity. A publisher signature validates the macro signer under platform policy. [Windows macro policy](https://learn.microsoft.com/en-us/microsoft-365-apps/security/internet-macros-blocked) · [Trusted publishers](https://learn.microsoft.com/en-us/microsoft-365-apps/security/trusted-publisher)
- Keep release permissions and credentials isolated from PR workflows. Pin automation dependencies, make workflow edits independently reviewable, use least-privilege tokens and retain promotion evidence. Store only synthetic test artifacts, aggregate study results and release metadata. Keep personal XLSM files, PDFs, values and assumption fingerprints out of model reviews, CI, issue reports and telemetry.
- Rehearse rollback before enterprise promotion. Restore the prior verified distributable and matching site links without overwriting users' files, then rerun privacy, checksum and compatibility smoke tests. For a suspected financial error, stop distributing the affected version, reproduce it with fictional data, record affected versions and publish the correction after independent reconciliation. Publish release notes with supported platforms, state/year scope, tested limits and recovery instructions.
